# ⚖️ 開発手法対比バランス (Methodology Balance)

## 1. 対比モデル (ウォーターフォール vs アジャイル)

開発手法はどちらか一方の手法が絶対的に有利にならないよう、トレードオフを対比させて設定します。

| 比較項目 | 🌊 ウォーターフォール開発 | 🔄 アジャイル開発 |
| :--- | :--- | :--- |
| **開発消化スピード** | **⚡ 爆速 (+30%)**<br>(一気に作る) | **🐢 やや遅い (-20%)**<br>(試作・レビュー調整) |
| **社内評価・上司信頼** | **🏢 高い (+10)**<br>(見通しが明確) | **⚠️ やや低い (-10)**<br>(完成時期が見通しにくい) |
| **品質・バグ混入率** | **🛡️ 通常バグ率 -20%**<br>(一括テストの強み) | **🐛 潜在バグが残りやすい**<br>(継ぎはぎ開発) |
| **仕様変更耐性** | **💥 致命的 (壊滅的大炎上)**<br>(後半の変更で全滅) | **🛡️ 極めて高い (柔軟にいなせる)**<br>(手戻りダメージ極小) |

---

## 2. 意思決定のジレンマ
* **要件定義WS等で「要件が固まった案件」** ➔ **🌊 ウォーターフォール** が絶対的に有利！
* **「どうしても要件が曖昧で変更がきそうな案件」** ➔ 速度低下を覚悟で **🔄 アジャイル** を選び、破滅的大炎上を防ぐ。
