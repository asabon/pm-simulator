# キックオフフェーズ再設計・検討案 (Draft)

本ドキュメントは、「キックオフフェーズ」を単なる確認画面ではなく、**「PMとしての学び（利害調整・トレードオフの受容）」と「ゲームとしての戦略性」を両立した魅力的なゲーム体験**へと進化させるための仕様検討ドラフトです。
ユーザー様との議論を通して、本ドキュメントの内容を繰り返し更新・洗練させていきます。

---

## 🎯 1. 設計思想と解決すべき課題

### 現状の課題
- **キックオフが「見るだけ」**: 案件情報やアサイン体制を確認し、「開始」ボタンを押すだけであり、PMとしての意思決定やジレンマが存在しない。

### 解決の方針（学習性 ✕ ゲーム性の両立）
- **× 従来のNGパターン**: 「APが足りないから顧客か現場のどちらかのヒアリングを諦める」
  - ➔ PMとして当然行うべき情報収集が制限され、不自然なモラハラ・怠慢プレイを強いられている感覚（モヤモヤ）が生じる。
- **〇 今回採用するパターン**: **「情報収集（ヒアリング）は全員無料」➔「浮き彫りになった無理難題（QCD全部盛り）の解決に AP を使う」**
  - ➔ 全員の話を聞くことで現実のPMが直面する**「顧客は要件が曖昧なまま、品質・納期・コストのすべてを完璧に求めてくる」というリアルな無茶振り**が可視化され、それを限られたAPや開発手法の選択でどう現実的なトレードオフへ着地させるかを思考・選択させる。

## 🏆 2. 「手段（開発手法）」と「統一された最終ゴール（評価指標）」の関係

開発手法（ウォーターフォール vs アジャイル）はあくまで**「ゴールを達成するための手段・アプローチの違い」**であり、最終的なプロジェクトの完了地点（クロージング画面）での評価指標は、**どんな手法を選んだとしても完全に統一された3大指標で評価**されます。

```
 【キックオフフェーズ（手段）】                     【最終クロージングフェーズ（統一ゴール）】

 🌊 ウォーターフォールを選択                            ┌─────────────────────────────────┐
 ➔ 事前の「要件確定度・計画精度」を高め、               │  🏆 統一3大評価指標              │
    納品時の品質・契約通り完成を目指す！              │                                 │
                                                ├─ 1. 👥 顧客満足度 (0〜100%)    │
                        ───────────────➔        │     (納期・品質・ニーズ適合度) │
                                                │                                 │
 🔄 アジャイルを選択                                    ├─ 2. 🏢 社内評価 / 上司信頼度    │
 ➔ 「スプリント適応度・共創体制」を高め、             │     (予算・進捗報告・リスク管理)│
    途中の試作改修で真のニーズ適合を目指す！           │                                 │
                                                ├─ 3. 🔥 チーム健全性             │
                                                │     (平均疲労度・士気・離職防止)│
                                                └─────────────────────────────────┘
```

## ⚖️ 3. 開発手法の絶妙なゲームバランス（ウォーターフォール vs アジャイル）

どちらか一方の手法が絶対的な有利（一択）にならないよう、現実のトレードオフを反映した**一長一短の強力なメリット・デメリット**を対比させて設定します。

| 比較項目 | 🌊 ウォーターフォール開発 | 🔄 アジャイル開発 |
| :--- | :--- | :--- |
| **開発消化スピード** | **⚡ 爆速 (+30%)**<br>(無駄な会議が無く一気に作る) | **🐢 やや遅い (-20%)**<br>(毎スプリントの試作・レビュー調整) |
| **社内評価・上司信頼** | **🏢 高い (+10)**<br>(全体納期・予算の見通しが明確) | **⚠️ やや低い (-10)**<br>(完成時期が見通しにくく上司が不安) |
| **品質・バグ混入率** | **🛡️ 通常バグ率 -20%**<br>(全体設計・一括テストの強み) | **🐛 潜在バグが残りやすい**<br>(継ぎはぎ開発になりがち) |
| **仕様変更耐性** | **💥 致命的 (壊滅的大炎上リスク)**<br>(後半の仕様変更で全滅) | **🛡️ 極めて高い (柔軟にいなせる)**<br>(仕様変更の手戻りダメージ極小) |

### 🎯 プレイヤー（PM）の意思決定ジレンマ
- **要件定義WS等で「要件がしっかり固まった案件」**:
  - ➔ 断然 **🌊 ウォーターフォール** が有利！消化速度+30%＆上司信頼度高めで楽々高得点が狙える。
- **「どうしても顧客の要望がふわふわしていて、後から変更を言いそうな案件」**:
  - ➔ 速度低下や上司の不安（ペナルティ）を覚悟の上で、**🔄 アジャイル** を選んで破滅的大炎上を防ぐリスクヘッジを行う。

## 💥 4. 顧客の初期スタンス：『QCD全部盛り ✕ 要件曖昧』モデル

現実のほとんどの顧客は、最初から「納期重視」や「品質重視」と分かりやすく割り切ってはいません。
**「要件はふわっとしているのに、品質も納期もコストも全て妥協したくない（100点満点を求めてくる）」** のが顧客の現実の初期スタンスです。

## 🔄 5. キックオフフェーズの3ステップ ＋ 最終決起構成案

```
 [Step 1: 情報収集（無料ヒアリング）]
    ・上司、顧客、PLの3者から話を聞く
    ・顧客の「QCD全部盛り無茶振り」と現場の「不可能性・パンク」が判明する
          │
          ▼
 [Step 2: PMの決断 ＆ ネゴシエーション (所有 AP: 3)] ★カテゴリ別UI ＆ 全アクション副作用付きトレードオフ！
    * 「対顧客」「対上司」「対現場」に整理された8つの選択肢から、AP 3 を使って戦略に合わせて事前調整
    * すべてのアクションに🟢プラス効果と🔴副作用/リスク（例: [要件確定度UP] ✕ [初期速度-10%]）が存在し、ノーリスクの正解コマンドを排除
    * 選択の【実行順序】に応じたステークホルダーのリアルタイムコメント・順序コンボが発生
          │
          ▼
 [Step 3: 開発手法の決定 (🌊 WF vs 🔄 アジャイル)]
    ・プロジェクト特性やStep 2での手応えに応じたデリバリー方針（手法）を選択
          │
          ▼
 🎉 [キックオフ最終イベント: 🔥 チームキックオフ決起 ＆ 防衛★診断]
    ・Step 2 の交渉結果と Step 3 の開発手法選択を総括するクライマックスイベント！
    ・チームメンバー（PL・現場）から熱い決起コメントと意気込みが送られる
    ・手法に応じた下準備強度（防衛★診断：要件確定度/適応度、期待値ギャップ、チーム安全度）が可視化
    ・「いざ、開発スプリント（第2フェーズ）へ突入！」ボタンで開発フェーズへ開始
```
