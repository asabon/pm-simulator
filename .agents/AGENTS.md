# PM Simulator - AI開発ガイドライン & ルール

本ドキュメントは、Google Antigravity が本リポジトリで作業する際に遵守すべき開発ルールとコンテキストを定義します。

---

## 🎯 プロジェクトの文脈
* **ゲーム概要**: プレイヤーが責任感を持って動き、ステークホルダーやチームをマネジメントする「プロジェクトマネージャー体験シミュレーションゲーム」
* **開発アプローチ**:
  1. **仕様化**: `docs/` 以下で、ゲームのコンセプトや仕様を文書化する。
  2. **プロトタイピング**: `prototype/` 内の Python CLI 版で、ゲームバランスとジレンマの面白さ、簡単な動作確認を行う。
     * ※ 迅速な原理確認のため、1 の「仕様化」と 2 の「プロトタイピング」は並行して進めてもよい。
  3. **本格開発**: 仕様やロジックが固まり合意が取れたら、Godot 4 (GDScript) による本格的な開発・UI実装に移行する。

---

## 🛠 AI支援開発の原則

### 1. 議論と仕様化の優先
* 実装に入る前に、必ずユーザーと議論を重ねて仕様を徐々に具体化・明文化すること。
* 大きな変更や新機能の追加時は、まず実装計画（Implementation Plan）を提示してユーザーの承認を得るプロセスを徹底すること。

### 2. ドキュメントの整合性
* 仕様に関する合意が得られたら、実装前に `docs/game_design.md` を必ず最新の状態に更新すること。コードと仕様書の間に乖離を作らないこと。

### 3. 技術的ルール
* **コード記述時のコア要件 (実装時必須)**:
  * **Python (プロトタイプ)**:
    * エントリポイントで標準出力をUTF-8に再設定（`sys.stdout.reconfigure(encoding='utf-8')` など）すること。
    * オブジェクト指向の明確な責務分け（データモデルとゲームエンジン）を意識すること。
    * コード変更時は `uv run ruff check --fix prototype/` および `uv run ruff format prototype/` を実行し、コードの静的解析・自動整形を行うこと。
  * **Godot 4 / GDScript (将来の移植時)**:
    * 静的型ヒント（型アノテーション）を徹底すること（例: `var score: int = 0`, `func update() -> void`）。
    * Controlノードのアンカーとコンテナ（HBox/VBox/Grid）を正しく設定し、レスポンシブなレイアウトにすること。
    * 辞書（Dictionary）変換可能なセーブデータシリアライズ設計を行うこと。
  * ※ PR発行前の詳細な品質検証項目・チェック手順については `.agents/skills/code-review/SKILL.md` を参照すること。

### 4. Git・ドキュメント駆動PR ＆ ブランチ管理ルール
* `main` ブランチへの直接のコミットおよびプッシュは**厳禁**とする。
* **【必須前提ステップ】ファイル変更着手前のブランチ自動検証 ＆ タイムスタンプ命名規則**:
  * ユーザーからコード修正・テキスト変更・仕様変更リクエスト（どんなに軽微な調整であっても）を受けた際、**ファイルを1文字でも編集する前に、必ず最初のツール実行として `git branch --show-current` を確認すること。**
  * 現在のブランチが `main` の場合は、**変更作業を開始する前に、直ちに専用ブランチ（`feature/xxx-MMDD-HHMM`, `fix/xxx-MMDD-HHMM`, `docs/xxx-MMDD-HHMM`）を新規作成・切り替えてから作業を開始すること。**
  * **ブランチ名重複防止ルール (必須)**: ブランチ名の末尾には必ず現在日時のタイムスタンプ（`MMDD-HHMM`）を付与し、ローカル・リモートでの過去ブランチ名との重複・衝突を100%防止すること。*(例: `feature/kickoff-dynamic-engine-0731-0622`, `docs/fix-markdown-layout-0731-0622`)*
* **仕様書駆動 ＋ PR 差分レビュー方式 (トークン節約＆仕様可視化の標準フロー)**:
  * タスクや仕様変更を行う際は、原則として **GitHub Issue は作成せず、直接ブランチを切って作業を開始** する。
  * チャットで議論・合意された仕様変更内容を、まず `docs/` 配下の該当ドキュメント（`docs/spec/` や `docs/design/`）に明記・更新した上で実装を行う。
  * **ユーザー様は PR の `docs/` 差分（File Changed）を見ることで「どんな仕様・設計に変更されたか」を一目瞭然でレビュー・把握・承認できる**構造を維持する。
  * （※長期的なプロジェクト管理などでユーザーから明示的な指示があった場合のみ、例外として `create-issue` スキルで Issue を起票する）
* **PR作成・自動クローズ ＆ マージ後完全クリーンアップフロー (`create-pr` スキルの実行)**:
  * ユーザーから PR の作成を依頼された場合（例: 「PR出してください」「PR作成」等）は、必ず `.agents/skills/create-pr/SKILL.md` のワークフローに従うこと。
  * スキル実行時に専門スキル（`code-review`, `doc-review`, `run-tests`）による自動検証・自動修正を行い、統一PRテンプレートを適用して GitHub CLI (`gh`) からPRを発行すること。
  * **PRマージ完了報告受託時**: ユーザーから「マージしました」等の連絡を受けた際は、**直ちに `git checkout main` ➔ `git pull origin main` ➔ `git fetch --prune` ➔ `git branch -d <branch_name>` の4ステップを連続実行し、リモート追跡情報も含めて100%完全クリーンアップ**すること。

## 📂 フォルダ構成のルール
* ドキュメントは `docs/` 配下に格納する。
* プロトタイプは `prototype/` 配下に格納する。
* カスタムスキルは `.agents/skills/<skill_name>/SKILL.md` に定義する。
* Godot関連のスクリプトは将来的に `scenes/` または `src/` 配下に構造化して配置する。
